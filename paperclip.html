Paperclip hoạt động như thế nào?

Từ một task đến một AI agent thực thi: Paperclip điều phối công việc, khởi chạy runtime như Codex hay Claude Code, thu nhận sự kiện và quản lý vòng đời session.

01 / Bức tranh toàn cảnh

Điều phối khác với thực thi

Paperclip không phải AI model. Nó là control plane: giao việc cho agent, chọn môi trường thực thi, theo dõi kết quả. CLI hoặc provider runtime mới là thành phần gọi model và sử dụng công cụ trên workspace.

01

Control plane

Task, scheduler/heartbeat, agent registry, authorization, budget và audit. Quyết định ai làm gì, khi nào.

02

Tạo execution context; chọn engine, gửi prompt, hiểu protocol, chuẩn hóa output và quản lý session.

        05 / Native Runner
        Core → Runner → Provider
        Native Runner là execution plane riêng, không chỉ là lệnh gọi CLI. Core chọn adapter paperclip_runner và provider đủ điều kiện, khởi chạy daemon Rust paperclip-runnerd tại môi trường thực thi. Runner mở kết nối PRP về Core, giám sát provider và session. Browser chỉ dùng Core API.

          06 / Session & coordination
          Vì sao nhiều agent không làm cùng một việc?
          Heartbeat
          Agent được kích hoạt theo sự kiện, lịch hoặc yêu cầu. Một run có run ID, task context và giới hạn thực thi.
          Checkout
          Task checkout có kiểm tra quyền sở hữu. Nếu đã được agent khác giữ, API có thể trả 409 Conflict; agent không tiếp tục task đó.
          Session resume
          Native ID cho phép nối lại hội thoại nếu workspace, runtime và cấu hình tương thích. Nếu mất session cần fresh context/handoff.
          

          Task khác Run, Session và Process ở điểm nào?
          Task là mục tiêu công việc; Run là một lần thực thi; Session là ngữ cảnh hội thoại của runtime; Process là tiến trình OS. Một task có thể có nhiều run, một session có thể được resume bằng nhiều process, và process exit chưa chắc task đã done.
          

          Native Runner có thay thế toàn bộ legacy adapter?
          Không. Hai đường có thể cùng tồn tại. Một số runtime mới có thể mặc định dùng Runner trên môi trường hỗ trợ; engine đã lưu không nhất thiết đổi theo. Core-to-Runner dùng PRP, provider driver giao tiếp với runtime riêng. Gemini được minh họa ở legacy CLI/ACP, không giả định có native Gemini driver.
          

          Điều gì xảy ra khi mất mạng?
          Disconnect không đồng nghĩa process đã dừng. Cần xác minh ownership, session/checkpoint và trạng thái side effect trước resume/retry. Không tự kết luận task thất bại hoặc chạy lặp khi kết quả chưa rõ.
          

          Áp dụng mô hình này cho một controller riêng như thế nào?
          Giữ control plane độc lập với runtime manager. Dùng driver process/stdio/PTY/HTTP làm lớp transport, adapter làm lớp encode/decode provider, registry để chọn engine, và event envelope chung. Đây là đề xuất thiết kế tổng quát, không phải sơ đồ thực thi nguyên bản của Paperclip.
